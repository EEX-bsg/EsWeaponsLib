# 設計思想

EWLに手を入れる前に読んでください。ここにあるのは「何を守るか」と「なぜそうしているか」です。
コードの構成は [architecture.md](architecture.md)、互換性の扱いは [compatibility.md](compatibility.md) にあります。

## EWLとは

E'sWeaponsLib(EWL)は、**外部Modの開発者(人とそのAIエージェント)が使う、Besiegeの汎用武装ライブラリ**です。
XMLカスタムモジュールとC# APIで、射撃・弾体・着弾・爆発・弾倉・ブロック物理・マルチプレイ同期を提供します。
E'sTankCannonsMod(E砲)が最初の利用者で、リファレンス実装を兼ねます。

## 変えない目的

1. 外部Modは**公開APIを通して** EWLを使い、内部の仕組み(弾体管理・同期・Besiege本体との接点)に関わらずに済む。
2. 外部ModはEWLの**XMLカスタムモジュールをそのまま**使える。
3. 外部ModはAPIで**独自に機能を足し、独自のカスタムモジュールを作れる**。

この3つは変えません。以下の原則・構成・APIの形は、これを満たすための手段です。目的を満たす限り変えて構いません。

## 原則

| 原則 | 内容と理由 |
|---|---|
| 公開APIが窓口、モジュールもその利用者 | EWL自身のXMLモジュールも公開API(`EWL.Api`)だけで書く。自分で使うことで「モジュールにはできて外部Modにはできない」穴が自然に塞がる。代わりに、機能1つにつき「APIのデータ・XML要素・変換」の3か所を書く |
| 新機能は内部 → API → モジュールの順 | XMLモジュールにだけある機能を作らない |
| 実装範囲は実需で決め、見せ方は汎用の語彙で | 何を作るかは実在の利用者(当面はE砲)の必要で決める。名前・XMLスキーマ・APIの形は特定のModに寄せず、汎用武装の言葉で設計する |
| 拡張は合成とイベントだけ | 利用側がEWLの部品(`Weapon` 等)を持って駆動し、イベントに反応する。継承用の基底クラス・フックの連鎖・レジストリ・DIは作らない。公開面を「データ + 部品 + イベント」に留めると、AIも誤用しにくく、保守も軽い |
| 概念を少なく | 型を分けるのは、独立して渡す・共有する定義(武装・弾・爆発)と、弾に付く任意機能(推進・誘導)だけ。話題ごとの箱は作らない。任意機能はnullではなく「0なら無効」の既定値で表す |
| MPは基準動作 | EWLのモジュールや `Weapon` で作った武装は、利用者が何もしなくてもMPで同期される |
| 互換は「緩く、しかし予告なく壊さない」 | 1.0までAPIの形を固めない。1.0以降も厳密な凍結はせず、壊すときは版を上げて移行手順を書く |
| 本体依存は追える場所に | 抽象層は作らない。落とし穴がある、または複数箇所で使うBesiege本体の操作だけを `Besiege/` にまとめる |

## 責務範囲

| 区分 | 内容 |
|---|---|
| EWLがやる | 射撃制御(キー・連射・バースト・遅延・拡散・反動)、弾体(生成・物理・コライダー・プール)、着弾(ダメージ・命中物へのくっつき・爆発・信管)、エフェクトと音、弾倉・リロード、推進、誘導、ブロック物理モジュール、MP同期、C# API、攻撃者のタグ(誰の弾・誰が起爆させたか)、利用者向けの文書とサンプル |
| 利用側Modがやる | ブロックのXML・アセット、HUDなどのUI、キル・デスの判定、そのMod固有の機能 |
| やらない | ACM(AddCustomModule)との互換(要素名・スキーマ・設定ファイル)、ワールド拡張(4km境界の突破・原点シフト)、水・浮力・環境・スカイボックス、武装と関係のない汎用基盤(他Mod向けの通信チャネルAPIなど) |

範囲の外に見える機能を足したいときは、実装の前にIssueで相談してください。

## 利用形態

| 形態 | 利用者が書くもの | EWLが担うもの |
|---|---|---|
| A. XMLモジュールをそのまま使う | ブロックXMLに `<EwlWeapon modid="...">` などを書く | 入力・射撃・弾体・着弾・爆発・エフェクト・MP同期の全部 |
| B. A + 観測 | Aに加え、C#で武装の状態やイベントを読む(残弾HUDなど) | Aと同じ |
| C. APIで独自モジュールを作る | 自分の `BlockModule` やブロックスクリプトで `Weapon` を作って駆動する。いつ・どう撃つか、値の出どころは利用者が決める | 弾体・着弾・爆発・エフェクト・弾倉・MP同期 |
| D. 独自機能を足す | Cに加え、下位の部品とイベントでEWLに無い挙動を書く | 部品それぞれの内側 |

形態Aのモジュールは形態Cと同じ公開APIだけで書かれています。つまり「EWLのモジュールでできること = 外部ModがAPIでできること」です。
形態Dの下位部品(弾体を直接扱う部品など)は、実際に必要になった時点で段階的に公開します。

## 判断に迷ったら

次の順に考えます。

1. 3つの目的のどれかを損なわないか。
2. 既存のブロックXMLや外部DLLを壊さないか([compatibility.md](compatibility.md))。
3. 実在の利用者が必要としているか(架空の需要のために作らない)。
4. 概念を増やさずに書けないか。
