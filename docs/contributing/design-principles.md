# 設計思想

EWL に手を入れる前に読んでください。ここにあるのは「何を守るか」と「なぜそうしているか」です。
コードの構成は [architecture.md](architecture.md)、互換性の扱いは [compatibility.md](compatibility.md) にあります。

## EWL とは

E'sWeaponsLib(EWL)は、**外部 Mod の開発者(人とその AI エージェント)が使う、Besiege の汎用武装ライブラリ**です。
XML カスタムモジュールと C# API で、射撃・弾体・着弾・爆発・弾倉・ブロック物理・マルチプレイ同期を提供します。
E'sTankCannonsMod(E砲)が最初の利用者で、リファレンス実装を兼ねます。

## 変えない目的

1. 外部 Mod は**公開 API を通して** EWL を使い、内部の仕組み(弾体管理・同期・Besiege 本体との接点)に関わらずに済む。
2. 外部 Mod は EWL の**XML カスタムモジュールをそのまま**使える。
3. 外部 Mod は API で**独自に機能を足し、独自のカスタムモジュールを作れる**。

この3つは変えません。以下の原則・構成・API の形は、これを満たすための手段です。目的を満たす限り変えて構いません。

## 原則

| 原則 | 内容と理由 |
|---|---|
| 公開 API が窓口、モジュールもその利用者 | EWL 自身の XML モジュールも公開 API(`EWL.Api`)だけで書く。自分で使うことで「モジュールにはできて外部 Mod にはできない」穴が自然に塞がる。代わりに、機能1つにつき「API のデータ・XML 要素・変換」の3か所を書く |
| 新機能は内部 → API → モジュールの順 | XML モジュールにだけある機能を作らない |
| 実装範囲は実需で決め、見せ方は汎用の語彙で | 何を作るかは実在の利用者(当面は E砲)の必要で決める。名前・XML スキーマ・API の形は特定の Mod に寄せず、汎用武装の言葉で設計する |
| 拡張は合成とイベントだけ | 利用側が EWL の部品(`Weapon` 等)を持って駆動し、イベントに反応する。継承用の基底クラス・フックの連鎖・レジストリ・DI は作らない。公開面を「データ + 部品 + イベント」に留めると、AI も誤用しにくく、保守も軽い |
| 概念を少なく | 型を分けるのは、独立して渡す・共有する定義(武装・弾・爆発)と、弾に付く任意機能(推進・誘導)だけ。話題ごとの箱は作らない。任意機能は null ではなく「0 なら無効」の既定値で表す |
| MP は基準動作 | EWL のモジュールや `Weapon` で作った武装は、利用者が何もしなくても MP で同期される |
| 互換は「緩く、しかし予告なく壊さない」 | 1.0 まで API の形を固めない。1.0 以降も厳密な凍結はせず、壊すときは版を上げて移行手順を書く |
| 本体依存は追える場所に | 抽象層は作らない。落とし穴がある、または複数箇所で使う Besiege 本体の操作だけを `Besiege/` にまとめる |

## 責務範囲

| 区分 | 内容 |
|---|---|
| EWL がやる | 射撃制御(キー・連射・バースト・遅延・拡散・反動)、弾体(生成・物理・コライダー・プール)、着弾(ダメージ・刺さる・爆発・信管)、エフェクトと音、弾倉・リロード、推進、誘導、ブロック物理モジュール、MP 同期、C# API、攻撃者のタグ(誰の弾・誰が起爆させたか)、利用者向けの文書とサンプル |
| 利用側 Mod がやる | ブロックの XML・アセット、HUD などの UI、キル・デスの判定、その Mod 固有の機能 |
| やらない | ACM(AddCustomModule)との互換(要素名・スキーマ・設定ファイル)、ワールド拡張(4km 境界の突破・原点シフト)、水・浮力・環境・スカイボックス、武装と関係のない汎用基盤(他 Mod 向けの通信チャネル API など) |

範囲の外に見える機能を足したいときは、実装の前に Issue で相談してください。

## 利用形態

| 形態 | 利用者が書くもの | EWL が担うもの |
|---|---|---|
| A. XML モジュールをそのまま使う | ブロック XML に `<EwlWeapon modid="...">` などを書く | 入力・射撃・弾体・着弾・爆発・エフェクト・MP 同期の全部 |
| B. A + 観測 | A に加え、C# で武装の状態やイベントを読む(残弾 HUD など) | A と同じ |
| C. API で独自モジュールを作る | 自分の `BlockModule` やブロックスクリプトで `Weapon` を作って駆動する。いつ・どう撃つか、値の出どころは利用者が決める | 弾体・着弾・爆発・エフェクト・弾倉・MP 同期 |
| D. 独自機能を足す | C に加え、下位の部品とイベントで EWL に無い挙動を書く | 部品それぞれの内側 |

形態 A のモジュールは形態 C と同じ公開 API だけで書かれています。つまり「EWL のモジュールでできること = 外部 Mod が API でできること」です。
形態 D の下位部品(弾体を直接扱う部品など)は、実際に必要になった時点で段階的に公開します。

## 判断に迷ったら

次の順に考えます。

1. 3つの目的のどれかを損なわないか。
2. 既存のブロック XML や外部 DLL を壊さないか([compatibility.md](compatibility.md))。
3. 実在の利用者が必要としているか(架空の需要のために作らない)。
4. 概念を増やさずに書けないか。
