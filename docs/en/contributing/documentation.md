# Writing Documentation

## Structure

| Location | Readers | How it is written |
|---|---|---|
| `README.md` | Everyone | The entry point. Directs each kind of reader to where they should go |
| `docs/getting-started.md` | Players | Installation and troubleshooting |
| `docs/guide/` | Mod developers | Handwritten. Procedures, ideas, and examples |
| `docs/reference/` | Mod developers | **Generated**. Do not edit by hand |
| `docs/contributing/` | Contributors | Handwritten. Design, structure, and conventions |
| `docs/llms.txt` | AI agents | A table of contents of all pages with one-line descriptions |
| `CHANGELOG.md` | Everyone | Only changes visible to users |

## Language

- The Japanese version is the source of truth. The English version is generated automatically from the Japanese version. Do not fix only the English version.

## Generating the reference

`docs/reference/` is generated by `tools/gen-reference.ps1` from the XML documentation output by the build (`///` comments) and the DLL.

```powershell
powershell -File tools/gen-reference.ps1
```

- To fix a description, fix the `///` comment in `src/` and regenerate.
- When an XML element has no description, the description of the corresponding C# field is used (directly under `EwlWeapon` → `WeaponSpec`, `Projectile` → `ProjectileSpec`, and so on).
  For elements that exist only in the module (items written with keys, sliders, or resource names), write `///` on the XML definition class.

## Website

`docs/` is built into a site with VitePress and published to GitHub Pages on a push to `main` (`.github/workflows/docs.yml`. A push with no changes under `docs/` does not build).
The page content remains ordinary Markdown, and the `#` heading at the top becomes the page title.

To view it locally, install Node.js (LTS) and, at the repository root:

```powershell
npm install          # Only the first time
npm run docs:dev     # http://localhost:5173 . Changes are applied automatically when you save
npm run docs:build   # The same build as publishing (fails if there is a broken link)
```

- When you add a page, also add it to the `sidebar` in `docs/.vitepress/config.mts` (and to `docs/index.md` and `docs/llms.txt`).
- If you write notes in the same style as GitHub (`> [!NOTE]`, `> [!WARNING]`, etc.), they are displayed in a framed box on the site too.
- You cannot reach outside `docs/` (such as `CHANGELOG.md` at the repository root) with a relative link. Write it as a URL on GitHub.
- Pages you do not want on the web are listed in `srcExclude` in `docs/.vitepress/config.mts` (they remain readable in the repository).
- The site also hosts the raw Markdown of each page (for example `/guide/csharp.md`). AI can follow it from `/llms.txt`.

## Things to watch when writing

- Do not write information that must not be made public: the decompiled output of the Besiege base game and internal implementation names learned from it, and information learned from other mods' source.
  Write Besiege's behavior in your own words as observable behavior. Check what can be checked mechanically with `tools/check-public.ps1`.
- Terminology: a module written in a block's XML is called an "XML custom module".
- Write units in square brackets such as `[m/s]`, `[s]`, and `[deg]`.
- Make examples work as they are. In XML examples, write only the necessary elements, on the assumption that omitted elements take their defaults.
- To make it easy for AI to read, keep to one topic per page and show the structure with headings and tables. When you add a new page, add it to `docs/llms.txt` and `docs/index.md`.
